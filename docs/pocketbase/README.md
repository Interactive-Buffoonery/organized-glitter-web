# PocketBase Schema History

For local app development without production data, use
[`local-development.md`](local-development.md).

For PocketBase JSVM hook development, route-scope gotchas, local hook testing,
and production upload cautions, use [`hooks.md`](hooks.md).

For the native app's complete owner-scoped snapshot and idempotent existing-record
edits, use [`mobile-sync.md`](mobile-sync.md).

This repo keeps PocketBase schema history in two separate places:

- `pb_migrations/` contains deployable migrations only. Files in that directory are
  executable PocketBase migration steps and should be safe to upload and run.
- `docs/pocketbase/migration-archive/` contains historical generated migrations for
  reference. Files in the archive are not deployment inputs.

## Rollback safety policy

Deployable migrations must be safe to upload and run against production-like
data. A migration `down` function must not silently delete user-entered data.

If rolling back would drop user-entered fields, collections, files, taxonomy,
relations, or preferences, the `down` function must throw an explicit error
instead of performing the destructive rollback. Production recovery for a
destructive schema mistake should be a backup restore or a purpose-built forward
migration, not a silent `migrate down`.

Rollbacks that only remove indexes or restore access rules are allowed when they
do not delete records, files, relation values, preferences, or expose cross-user
data. Local-only resets should use `pnpm pb:bootstrap:local -- --seed` or a
local schema import instead of relying on destructive down migrations.

Run the static migration safety check before deployment:

```bash
pnpm pb:validate:migrations
```

## SFTP migration deploys

For INT-1084, deploy the two dashboard-generated revision field migrations
(`1790568959_updated_projects.js` and
`1790568959_updated_coloring_books.js`) before the revision and coloring hook
changes. Deploy the web build only after both migrations and hooks are active.
Existing rows read as revision zero; later project or coloring book record saves
and direct tag-link changes increment it. Derived sort-proxy SQL maintenance does
not change the revision. Older clients may omit the expected-revision header and
remain writable. Web edit forms send `X-OG-Expected-Revision`; when their tag
selection changed, they also send `og_tag_ids` as a JSON array string in the
update body. The hook validates at most 1,000 IDs and 1,000 link changes, then
saves the parent and links in one transaction. Keep `tag_revision_helpers.js`
with the revision and coloring hooks when deploying; the hooks must never run
against a schema without the new fields. Both request hooks load the shared
guarded-update handler inside their callbacks. It validates the expected
revision and owner, saves the parent and tags, and restores the request app
after the transaction. Header-free coloring book updates also use this
transaction so page cleanup remains atomic; header-free project requests
continue directly.
Rehearse this order on a disposable or production-like copy and verify a
header-free update, an accepted guarded update, and a stale HTTP 409 before
releasing the web build. Do not roll back the fields after writes because doing
so would erase revision history.

PocketBase migrations are deployed by explicitly selecting the migration files for
the current change, uploading only those files over SFTP, and then running the
PocketBase migration command on the target environment.

Do not sync or upload the whole `pb_migrations/` directory unless the target
environment's migration history has been reconciled against every file in that
directory.

## Coloring book schema notes

`coloring_books.is_mystery` is optional in PocketBase so records can represent
standard coloring books as well as mystery coloring books. App code should still
send an explicit boolean when creating or updating books:

- `false` means a standard, non-mystery coloring book.
- `true` enables mystery-page reveal behavior.
- omitted or legacy missing values should be treated as non-mystery at app
  boundaries.

When changing this field, update the deployable migration, the committed schema
snapshot, and the generated TypeScript contract together. The current app
service default lives in `src/services/pocketbase/coloring.service.ts`.

## Generated TypeScript contract

`src/types/pocketbase.types.ts` is the generated app contract used by TypeScript.
It should stay committed, but it is not a complete schema backup and does not
replace either deployable migrations or archived schema history.

## Dashboard settings JSON fields

`user_dashboard_settings.randomizer_next_up` stores durable per-mode randomizer
pins separately from `randomizer_spins`. The app normalizes malformed values
back to `{ "version": 1, "targets": {} }` and writes only this column when a
user saves or clears a next-up pick.

`user_dashboard_settings.user` is unique because all settings fields share one
row. Deploy `pb_migrations/1788705263_updated_user_dashboard_settings.js` only
after confirming there are no users with duplicate settings rows. The migration
fails without changing records when duplicates exist because their
`vertical_enabled` history cannot be merged safely from row-level timestamps.
The service recovers a concurrent first-write conflict by loading the row that
won creation and applying the other field-specific update.

`randomizer_spins.selected_count` allows a minimum of `1` so a one-target pool
can still produce a durable spin-history record.

## Native artwork thumbnails

Deploy `pb_migrations/1790500000_add_native_artwork_thumbs.js` to add
`480x600f` and `960x1200f` (4:5 thumbnails that fit without cropping) to `projects.image`,
`coloring_books.cover_image`, `coloring_pages.photos`, `progress_notes.image`,
and `coloring_page_progress_notes.image`. All existing sizes remain available,
including `300x200` and `600x400` on `projects.image`.

Native clients can request `?thumb=480x600f` or `?thumb=960x1200f` with the
existing protected-file token. Unlisted sizes such as `320x420` still return
the original file. Originals, web requests, access rules, and older clients
remain unchanged. Rollback removes only the two new sizes from these fields.

PocketBase thumbnails only JPEG, PNG, GIF (first frame), and WebP, so HEIC and
HEIF uploads keep returning the original at these sizes. The rollback deletes
no originals: removed sizes fall back to the original file like any unlisted
size.
